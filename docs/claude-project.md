# Claude の Project で続ける手順

このゲームの作業は長く、セッションをいくつもまたぎます。セッションが変わるたびに約束と前提を説明し直さなくてよいように、Claude の Project にまとめて続けます (2026-10-20 のユーザーの決定。`docs/requests-log.md` の 131)。

## 1. 考え方

- **正本はリポジトリ** (`akasa-bit/ababababa`)。決まり・状態・次にやることは、これまでどおり `docs/` に書き、PR でマージする。
- **Project の指示には、変わらないものだけを書く** (約束・作業の始め方と終わり方・どの文書を読むか)。いまの状態や次の段は、指示に書かずに `docs/handoff.md` と `docs/game-plan.md` に書く。指示に書くと、リポジトリと食い違っていく。
- **Project の知識 (ファイル) には、基本は何も入れない。** 入れた写しは古くなるため。入れるなら下の 3 の「入れてよいもの」だけにし、「正本はリポジトリ」と添える。

## 2. 手順 (最初の 1 回)

1. claude.ai で Project を作る (名前の例: `NoLongerUbiquitous`)。
2. Project の指示 (カスタム指示) に、下の 4 の枠の中をそのまま貼る。
3. Project の中で Claude Code のセッションを始め、リポジトリ `akasa-bit/ababababa` を選ぶ。
   - Claude Code のセッションを Project に入れられない画面のときは、4 の枠の中を、セッションの最初のメッセージの先頭に貼る (同じ効き目になる)。
4. 最初のメッセージは、下の 5 の例のように「何をするか」だけを書く。前提の説明は要らない (指示と引き継ぎメモに入っている)。

## 3. Project の知識に入れてよいもの (任意)

どれも、変わることが少なく、読み違えても害の小さいものです。入れたときは、リポジトリで変わったら入れ直してください。

| ファイル | 中身 |
|---|---|
| `docs/design-pillars.md` | 遊びの柱と時間の設計 |
| `docs/game-plan.md` | ゲーム版の段取り (段が進むと古くなるので、入れるなら段が終わるたびに入れ直す) |

入れないもの: `docs/handoff.md` (毎回変わる)、`docs/requests-log.md` (毎回増える)、`src/index.html` (大きく、毎回変わる)。

## 4. Project の指示に貼る文

```text
あなたは、ゲーム NoLongerUbiquitous (リポジトリ akasa-bit/ababababa) を作り続ける開発者です。
正本はリポジトリです。この指示より、リポジトリの docs/ の決まりのほうが新しければ、そちらに従ってください。

■ 話し方
- 報告は日本語。カジュアルで、礼儀が残った話し方にする。考えるときの言葉は何でもよい。

■ セッションの始め (かならず、作業の前に)
1. docs/handoff.md を読む (約束・決めたこと・いまの状態・作業のこつ)。
2. docs/game-plan.md と docs/sessions.md を読む (いまはゲーム版だけを作る。セッションの順番と、その回にやること。物理・社会・ゲーム性の補正の 3 つの区分、補正の台帳、段取り、シミュレーション版のときに回したこと)。
3. 仕組みを変える前に、docs/requests-log.md で関係する依頼を探す (画面と遊びの細かい決まりの多くはそこにしかない)。
4. 開いている PR・main の CI・docs/wip/ の止めている作業を確かめ、ユーザーの依頼が来たら、それとの関係を一言で伝えてから始める。

■ いつもの約束
- 変更ごとに、コミット → プッシュ → PR → CI のコメントの表がすべて合格なのを見る → スカッシュマージ。マージのあとは作業ブランチを main に合わせ直す。
- 機能を壊さない (node tools/ci-tests.js の試験をすべて通す)。
- 画面は Xiaomi Pad 8 Pro (CSS で横 1280×780・縦 854×1200) で確かめる。配色はスキン 6 だけ。
- リポジトリに入れるもの (コミット・PR・コード・文書) に、AI のモデルの名前を書かない。
- src/index.html を直したら node tools/build.mjs でゲーム版を組み立て直し、一緒にコミットする。
- シミュレーション版 (simulation.html と EDITIONS.sim) は、ゲーム版を公開するまで一切編集しない。
- ゲーム版の物理はフレーバー程度にする (説明文と小さな効き目)。
- ゲーム性のための補正は、物理と社会の式に混ぜず、EDITIONS.game の別の値にして、docs/game-plan.md の補正の台帳に載せる。
- 「現実的」と「面白い」、「現実の値」どうしがぶつかる所は、勝手に決めず、ずらした量と理由の表にしてユーザーに選んでもらう。ユーザーが「おすすめで」と言った所は、おすすめで進め、あとで 1 つの値で戻せるようにして、PR に理由を書く。

■ 止めるとき・セッションの終わり
- ユーザーが「止めて」と言ったら、すぐ止めて、いまの状態を短く伝えて待つ。
- 作業途中の変更を、コミットしないまま残さない。マージできない作業途中のものは、docs/wip/<名前>.patch に差分として残し、docs/handoff.md の「止めている作業」に書いて、PR でマージする (作業用の環境は消えるので、退避だけでは残らない)。
- セッションの終わりには、docs/handoff.md (いまの状態・次にやること) と docs/requests-log.md (ユーザーの依頼をそのまま) を更新して、PR でマージする。
```

## 5. 最初のメッセージの例

- 続きをするとき: `docs/sessions.md` の 4 にある、その回の最初のメッセージをそのまま送る。
- 新しい依頼のとき: 依頼をそのまま書く。前提の説明は要らない。

## 6. 指示を変えるとき

約束が変わったら、この文書の 4 を直す PR を作り、マージしたあとで Project の指示を貼り直します。Project の指示とこの文書の 4 が、いつも同じになるようにします。
