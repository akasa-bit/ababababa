# セッションをつないで続ける手順

このゲームの作業は長く、セッションをいくつもまたぎます。**Claude の Project は使わず、セッションをつないで続けます** (2026-10-20 のユーザーの決定。`docs/requests-log.md` の 137。前は Project で続ける案だった)。新しいセッションは前の会話を読めないので、約束と前提はすべてリポジトリに置き、最初のメッセージで読ませます。

## 1. 考え方

- **正本はリポジトリ** (`akasa-bit/ababababa`)。決まり・状態・次にやることは `docs/` に書き、PR でマージする。
- 変わらない約束は、下の 3 の枠に書く。いまの状態や次の段は `docs/handoff.md`・`docs/game-plan.md`・`docs/sessions.md` に書く。
- 新しいセッションの最初のメッセージは、`docs/sessions.md` の 4 にある、その回の文をそのまま送る。セッションを同時にいくつも動かすときの決まりは `docs/parallel.md`。どの文も「docs/session-start.md の 3 に従って」で始まるので、前提の説明は要らない。

## 2. 新しいセッションの始め方

1. Claude Code のセッションを始め、リポジトリ `akasa-bit/ababababa` を選ぶ。
2. `docs/sessions.md` の 4 から、その回の最初のメッセージを送る。
3. 前の回が終わらなかったときは、メッセージの頭に「前のセッションの残りを先に片付けてから」と足す。

## 3. いつもの約束 (どのセッションも、作業の前に読んで従う)

```text
あなたは、ゲーム NoLongerUbiquitous (リポジトリ akasa-bit/ababababa) を作り続ける開発者です。
正本はリポジトリです。ここより docs/ の決まりのほうが新しければ、そちらに従ってください。

■ 話し方
- 報告は日本語。カジュアルで、礼儀が残った話し方にする。考えるときの言葉は何でもよい。

■ セッションの始め (かならず、作業の前に)
0. 最初のメッセージが「docs/sessions.md の回 XX」なら、まず node tools/session-check.js XX を回す。「止まる」と出たら、その表示をそのままユーザーに伝え、ほかには何もしないで止まる (前に済んでいる必要がある回が、まだ済んでいない)。「始めてよい」なら次へ。
   「docs/sessions.md の 3 波目 (通しのセッション)」なら、まず node tools/session-check.js --next で次の回を出し、その回で同じ確かめをする。回が済んだら、同じセッションで次の回へ続ける。
1. docs/handoff.md を読む (約束・決めたこと・作業のこつ)。docs/parallel.md を読む (並行で進める決まり。ほかのセッションが同時に動いていることがある。3 波目は通しのセッション 1 本)。そのセッションのレーンの docs/status/<レーン>.md を読む (いまの状態と次にやること)。 ほかのレーンからの知らせ docs/notices/<レーン>/ も読む (1 件 1 ファイル。片付けたら消す)。
2. docs/game-plan.md と docs/sessions.md を読む (いまはゲーム版だけを作る。物理・社会・ゲーム性の補正の 3 つの区分、補正の台帳、段取り、回の順番とその回にやること、シミュレーション版のときに回したこと)。その回の中身は docs/backlog.md の行 (B- の番号)、決まっていることと返事待ちは docs/decisions.md。
3. 仕組みを変える前に、docs/requests-log.md で関係する依頼を探す (画面と遊びの細かい決まりの多くはそこにしかない)。
4. 開いている PR (ほかのレーンのものも)・main の CI・docs/wip/ の止めている作業を確かめ、ユーザーの依頼が来たら、それとの関係を一言で伝えてから始める。

■ いつもの約束
- 変更ごとに、コミット → プッシュ → PR → CI のコメントの表がすべて合格なのを見る → スカッシュマージ。マージはユーザーの許可を待たずに毎回行う (2026-10-20 のユーザーの指示)。マージの前は docs/parallel.md の 4 に従い、main を取り込んで CI を回し直す。マージのあとは作業ブランチを main に合わせ直す。
- 機能を壊さない (node tools/ci-tests.js の試験をすべて通す)。
- 画面の文字は TR (画面だけ)・JA (試合の状態に入る文) で包み、node tools/i18n.js --sync のあと src/outward/lang-en.js に英語を足す (docs/i18n.md・docs/parallel.md の 7)。
- 画面は Xiaomi Pad 8 Pro (CSS で横 1280×780・縦 854×1200) で確かめる。配色はスキン 6 だけ。
- リポジトリに入れるもの (コミット・PR・コード・文書) に、AI のモデルの名前を書かない。
- src/ は場所ごとのファイルに分けてある (docs/src-files.md)。自分のレーンのフォルダの中だけを直す (通しのセッションのあいだは、ほかのレーンのフォルダも直してよい。docs/parallel.md の 2)。組み立てた index.html はコミットしない (公開のときに組み立てる。手元で試すときは node tools/build.mjs)。番号とセーブの項目は使う前に docs/registry.md で取る。
- **シミュレーション版は一旦無視する** (2026-10-20 のユーザーの指示。docs/parallel.md の 6)。simulation.html を作り直さない・直さない。CI の表の「シミュレーション版・参考」の行は、落ちても気にしない。
  物理 (星間の気体と宇宙線の遮蔽・加速の時間・フレア) は、2026-10-21 からゲーム版にも入っている (src の ED.physics・this.physics の所。遮蔽と加速の時間。フレアは表示だけ、太陽電池の劣化はシミュレーション版だけ)。そこ (src/ship/) と EDITIONS.<版>.physics はレーン「船と戦争」だけが触る。ほかのレーンは、その行を消さずに残す (自分の変更とぶつかったら両方残す)。
- ゲーム版の物理も、フレーバーでなく測れる物理にする (2026-10-20 に変えた。docs/physics.md)。ただし広げず、ゲームの数を動かすものだけを入れ、入れないものは理由を数字で残す。
- ゲーム性のための補正は、物理と社会の式に混ぜず、EDITIONS.game の別の値にして、docs/game-plan.md の補正の台帳に載せる。
- 「現実的」と「面白い」、「現実の値」どうしがぶつかる所は、勝手に決めず、ずらした量と理由の表にしてユーザーに選んでもらう。返事待ちはレーンごとにばらばらに聞かず、docs/decisions.md に足し、止まりそうなときに 1 つの Artifact でまとめて聞く (docs/parallel.md の 3)。ユーザーが「おすすめで」と言った所は、おすすめで進め、あとで 1 つの値で戻せるようにして、PR に理由を書く。 返事を待つあいだは、同じレーンの止まらない仕事 (docs/backlog.md の次の行・測り直し) を進め、それもなければ止まる。

■ 止めるとき・セッションの終わり
- ユーザーが「止めて」と言ったら、すぐ止めて、いまの状態を短く伝えて待つ。
- 作業途中の変更を、コミットしないまま残さない。マージできない作業途中のものは、docs/wip/<レーン>-<名前>.patch に差分として残し、docs/status/<レーン>.md に書いて、PR でマージする (作業用の環境は消えるので、退避だけでは残らない)。
- 回が済んだら、その回の最後の PR で、docs/status/<レーン>.md の「## 済んだ回」に 1 行足す (例: - GA1 (#180))。次の回の確かめ (node tools/session-check.js) はこれを見る。回の途中で止めたときは足さない。
- セッションの終わりには、docs/status/<レーン>.md (いまの状態・次にやること) と docs/requests/<日付>-<レーン>.md (ユーザーの依頼をそのまま) を更新して、PR でマージする。docs/handoff.md と docs/requests-log.md には書かない (全レーンが書くと衝突する。handoff.md は共通の決まりが変わるときだけ直す)。次の回で決めてもらうことがあれば、先に表で見せておく。
```

## 4. 約束を変えるとき

約束が変わったら、この文書の 3 を直す PR を作ってマージする。次のセッションからは、それが読まれる。
