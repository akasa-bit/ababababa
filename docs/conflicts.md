## 1. 数え方

- 対象: レーンに分かれた #115 から #172 までの PR 58 本 (マージ 55・閉じた 1・開いたまま 2 = #117・#154)。比べるために、回 R1 で #117・#154 に main を取り込んだ 2 回も別に数えた。
- (a) **取り込み直しの回数**: PR のコミットのうち、親が 2 つあるもの (「main を取り込む」「Merge … origin/main」)。同じコミットが積み重ねのブランチで後の PR にも出るときは、最初の PR だけで数えた。
- (b) **衝突の回数**: その取り込みを `git merge-tree` で同じ 2 つの親からやり直し、手で直す必要のあったファイルを数えた。`src/index.html` と文書は、衝突の印のある所を、囲む関数・定数の名前 (文書は見出し) に読み替えた。「両側が触った」は、共通の祖先から見て両側が同じ関数・見出しを変えたもの (git が自動で混ぜられたものも含む)。
- (c) **main の上で何レーンが触ったか**: main のスカッシュのコミットごとに、`src/index.html` の変わった行を関数の名前に読み替え、何本の PR・何レーンが同じ所を触ったかを数えた (衝突の起きやすさ)。
- (d) PR の本文と、状態のファイルの「落とし穴」の書き込み (番号のずらし・取り込み直し)。
- 限り: レーン C のブランチ (`ccr-d95b56c7`) は取り込みではなく作り直し (rebase) をしていたので、#122〜#144 の C の取り込み直しは数に出ていない。実際はもっと多い。

## 4. わかったこと (ファイル分けと番号の予約のために)

- **組み立てた `index.html` をコミットしないだけで、衝突の約 8 割が消える。** 衝突した 20 回のうち 16 回にこのファイルがあり、7 回はこれだけだった。直し方はいつも「組み立て直す」だけで、考える所はない。公開 (`.github/workflows/pages.yml`) に組み立てを足して、リポジトリから外すのがいちばん効く (`docs/restart.md` の 5)。
- **セーブは「仕組みごとに登録する」形にする。** 中身の衝突の 4 分の 3 が `buildSave` の同じ 1 行だった (A の `shipHist`、C の `market`・`productivity`、P の `pvPolicy`・`physics`)。`buildSave`・`constructor`・`restore` の 3 か所を、仕組みのファイルごとに「自分の項目の書き出し・読み込み・初期値」を登録する形にし、どうしても残る一覧は 1 行に 1 項目にする。
- **ファイルの分け方は「関数の持ち主」で決める。** 物理の関数は P、経済の関数 (`economy`・`fiscalHtml`・`setFiscal`・`interestStep` など) は C だけが触っていて、ほとんどぶつからなかった。ぶつかったのは持ち主が 2 つある所: 統治体制と離反 (C と H) → 「政治」に寄せ、C の税の重さは政治のファイルが呼ぶ関数にする。`snapshot`・`onPanelChange`・`advance`・`exec` のような「みんなが 1 行ずつ足す」所は、仕組みごとに登録する形 (表示の切り替えはタブごとのファイル、年ごとの処理は登録した関数を順に呼ぶ) にしてから分ける。`tools/ci-tests.js` の `TESTS` と `data/README.md` も、ファイルを置けば見つかる形 (または 1 項目 1 ファイル) にする。
- **番号は使う前に予約する (`docs/registry.md`)。** 目標の番号 (R28 を A と C が、版 7 を A・S・C が同時に使おうとした)、レーンの名前 (P を物理と下準備が使い、下準備を Q に変えた #128)、補正の台帳の番号 (C)、依頼の番号を、PR を出す前に 1 行書いて予約する。版は「マージする PR が上げる」と決め、予約した番号は版と別に持つ。
- **同じレーンでも、ブランチを積み重ねない。** H は前の PR のブランチの上に次を作り、前がスカッシュでマージされると自分の変更とぶつかった (#166・#169・#170)。P は 2 つの回 (#154 と #161) が同じ物理の関数を並んで触った。次の回は、前の PR がマージされた main から始める。同じ場所を触る回は、同じレーンでも並べない。
