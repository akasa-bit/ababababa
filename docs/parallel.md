### レーン U (画面) の決まり

- **画面だけを触る。** CSS・配置・タブ・描画の関数・`ICONS` だけを直す。画面に新しい値を出したいときは、`known` (スナップショット) に値を足すだけの小さな PR にし、PR の本文にそう書く。
- **ほかのレーンが作っている画面は避ける。** 始める前に `docs/status/` と開いている PR を見て、作業中の画面 (B の同意の画面・C の市場の表示など) には手を出さない。人口と集団 (レーン D) が入ると星系の画面に内訳が増えるので、そこは作り込みすぎない。
- **これまでの画面の決まりを守る。** `docs/handoff.md` の 15 (スキン 6・額縁の枠・古い報告書風の書体・文字の 4 段階・押したボタンが指から逃げない・説明は「説明」を押したときだけ など) と、`docs/requests-log.md` の画面の依頼。変えたいときは、変える前に表にしてユーザーに選んでもらう。
- **アイコンは、候補を見せてユーザーに番号で選んでもらう** (これまでと同じやり方。`docs/requests-log.md` の「選んだアイコン」)。出典とライセンスは README の「アイコンの出典」に足す。
- **PR は画面 1 つずつ、小さく早く。** 画面は Xiaomi Pad 8 Pro の横 (1280×780) と縦 (854×1200) で撮り、前と後を並べて PR に書く。画面を操作する試験 (`pick`・`rotate`・`edit`・`home` など) を通す。

### レーン S (Steam) の決まり

- 包装は、組み立てた `index.html` を外から包むだけにする。ゲームの中身・`tools/build.mjs`・CI は変えない (包装のための変更が要るときは、その所だけを小さな PR にして、PR の本文に書く)。
- 包装の組み立てと試験の台本は `desktop/` の中に置く。CI に足すのは、包装が決まってから (B と相談)。
- ストアの文・画像の案・Steamworks の手順は `store/` に置く。ゲームの中の文字列には触らない (文字列を集めるのはセッション 18)。
- Steamworks のアカウント・支払い・税の書類など、ユーザーにしかできないことは、手順の一覧にしてユーザーに渡す。代わりに登録しない。

### レーン Q (下準備) の決まり

後の回が最初にユーザーの返事待ちで止まらないように、選択肢の表と生データを先に用意するレーン。ほかのレーンとぶつからないように、次を守る。

- **新しいファイルだけを作る。** `src/`・`tools/`・`index.html` には触らない。共有のファイル (`data/README.md`・`data/raw/MANIFEST.json`・`docs/game-plan.md`・`docs/handoff.md`) にも書かず、取った生データは `data/raw/<名前>/` に、その中の `MANIFEST.json` と `README.md` をつけて置く。
- **目標 (`targets/targets.json`) は変えない。** 幅の案は `docs/proposals/` に書くだけにし、固定はその段のセッションが「目標の変更」の PR で行う (目標の PR は 1 本ずつ)。
- **ほかのレーンが動いている段には手を出さない。** 始める前に `docs/status/` を読み、その段のセッションが始まっていたら、その段の分は飛ばす。
- ユーザーの返事は `docs/requests/<日付>-Q.md` にそのまま残し、`docs/proposals/` の表に「決まった案」として書く。その段のセッションは、決まっていればそれに従い、もう一度は聞かない。

## 2. 文書の分け方 (衝突しないように)

全員が書き足すファイルを作らない。

| 何を | どこに | 決まり |
|---|---|---|
| ユーザーの依頼 (そのまま) | `docs/requests/<日付>-<レーン>.md` (例: `2026-10-21-A.md`) | 番号は `<レーン>-<通し番号>` (例: A-1)。通し番号はそのファイルの中だけで数える。並行の前の依頼は `docs/requests-log.md` (1〜137。セッション 1 が足す分まで) |
| レーンのいまの状態と次にやること | `docs/status/<レーン>.md` | そのレーンのセッションだけが書く |
| 止めている作業の差分 | `docs/wip/<レーン>-<名前>.patch` | 書いたら `docs/status/<レーン>.md` に載せる |
| 全レーンに共通の約束・文書の地図・作業のこつ | `docs/handoff.md` | 共通の決まりが変わるときだけ直す (いまの状態は書かない) |
| 段取り・補正の台帳 | `docs/game-plan.md` | 段が終わったときと、台帳に行を足すときだけ。足すときは表の末尾に 1 行ずつ (並べ替えない) |

レーンに入らない相談 (段取りや決まりの話) は、レーン名を `common` にする (`docs/requests/<日付>-common.md`・`docs/status/common.md`)。

## 3. マージの前

1. main を取り込む (`git fetch origin main && git merge origin/main`)。
2. `index.html` (組み立てたもの) が衝突したら、手で直さず `node tools/build.mjs` で作り直す。
3. `node tools/ci-tests.js` を通してから push し、**CI をもう一度回す**。自動対戦の表は main と比べるので、main が動いたあとの表でないと当てにならない。
4. 新しい表がすべて合格になってからマージする (マージはユーザーの許可を待たない)。
5. 目標 (`targets/targets.json`・`targets.lock`) を変える PR は、ほかのレーンに同じものが開いていないか確かめ、1 本ずつ出す。
6. PR は小さく、早めにマージする (長く開けておくほど衝突が増える)。

GitHub の設定 (branch protection の *Require branches to be up to date before merging*) をオンにすると、1 を忘れても GitHub が止めてくれる (ユーザーの設定)。

## 4. 始め方

- レーンごとに Claude Code のセッションを 1 つずつ開き、`docs/sessions.md` の 4 にある、そのセッションの文を送る。
- 文の終わりに、ほかに動いているレーンを書き足す (例:「いま A と C も並行で動いている」)。
